## The Central Adjudication — the incumbent-perturbation question

The orchestrator flagged the incumbent perturbation (the engineering report finds TRX IS net PnL swung +3.95% → −23.04% on FIL's addition, with BCH and LDO also moved) as the make-or-break call. The mandate: is this a **legitimate consequence** of universe expansion (→ valid NEGATIVE, OVERALL=MERGE) or a **bug** — cross-symbol leak / seed misallocation / 4-symbol mishandling (→ OVERALL=BLOCK)?

I traced the runner's per-symbol seed / CV / gap handling end-to-end. **Conclusion: the incumbent perturbation is NOT a bug. The run is methodologically sound.** Evidence:

1. **Per-symbol model isolation is total.** `_run_single_seed` (`run_baseline_v3.py:2349-2381`) iterates `for name, symbol in models_to_run` and calls `_build_v3_model(symbol=symbol, seed=seed, n_trials=n_trials, ensemble_seeds=ensemble_seeds_run, ...)`. Every argument to `_build_v3_model` for BCH/LDO/TRX is **byte-identical whether `V3_MODELS` has 3 or 4 entries**: `seed` is constant, `n_trials=35` is constant, `ensemble_seeds_run` is the constant tuple `[191664963, 1662057957, 1405681631]`, and `_build_v3_model` (`run_baseline_v3.py:1702-1761`) builds each model with `symbols=(symbol,)` and `feature_columns=list(features_for_symbol(symbol))`. **There is no `len(V3_MODELS)` dependency anywhere in `_build_v3_model` or in the per-symbol Optuna study.** Each symbol gets its own independent Optuna `study` ("A new study created in memory" per FIL's training log) with its own TPE sampler.

2. **The engineering report's stated mechanism is mechanistically false.** The report (Core Diagnostic / Screen-vs-Reality sections) attributes the TRX swing to *"TRX's Optuna-selected hyperparameters at the 4-symbol landscape differ from those at 3-symbol"* and *"Adding a 4th symbol changes the per-cell training-sample distribution and Optuna search dynamics for BCH, LDO, and TRX."* **There is no such thing as a per-incumbent "4-symbol Optuna landscape."** TRX's Optuna study sees only TRX's training samples; it is identical to the 3-symbol run's TRX study. This is a false causal claim in the engineering report — not a bug in the *run*, but an analytical error in the *report*.

3. **The post-model filters are stateless.** `apply_btc_trend_filter` (`risk_v2.py:1130-1188`) is a pure per-trade filter — each trade's kill decision depends only on that trade's `open_time`/`direction` and the BTC kline series; there is zero cross-trade state, zero pooled aggregation. A TRX trade's outcome cannot depend on FIL's presence in the book. `apply_hit_rate_gate` activates only at `OOS_CUTOFF_MS` and is config-disabled. The only genuinely pooled computation is `_compute_cpcv_paths` — and that is a **downstream reporting artifact** (the CPCV return-proxy sequence), computed *after* the trade roster is fixed; it cannot retroactively change which trades TRX takes.

4. **The actual cause is the Phase-6 data re-fetch — a legitimate, sanctioned consequence.** Brief Section 3.6 mandates re-fetching **all four** symbols' 8h klines and regenerating all features in this worktree (per `feedback_data_staleness_per_worktree.md`). The /059 baseline numbers were produced at commit `bea0987` on a different data extent. BASELINE_V3.md's own "EXPLORATION-Mode Anchor Staleness" section establishes (the /077 finding) that the /059 config no longer reproduces bit-identically on current code+data — there is a documented IS code-drift + OOS data-extent drift. Re-fetching TRX's klines revises/extends its series; feature recomputation shifts TRX's marginal feature values; TRX is a structurally low-edge symbol (29-34% WR) where small feature shifts flip many marginal trades. This is the legitimate, expected consequence of running a fresh backtest on freshly-fetched data — not a leak.

One precision note for the QR (does not change the verdict): the brief Section 4.3 pre-registered that incumbent rosters "CAN shift" but attributed the mechanism to "`REQUIRED_GAP` rises 66→88 [changing] the embargo." That attribution is also imprecise — `REQUIRED_GAP` enters **only** the pooled CPCV path computation (a reporting artifact); it does not touch the per-cell walk-forward embargo (fixed at 22) and therefore cannot change the trade roster. The brief's *prediction* (incumbents can shift) is correct; the brief's and the engineering report's *stated mechanisms* are both wrong. This is a methodology-*reporting* imprecision, not a methodology *defect* in the run — the run itself is sound (correct gap, correct embargo, no leak, no seed misallocation, total feature isolation). The result is a valid NEGATIVE.
