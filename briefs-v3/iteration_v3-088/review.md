## Per-Check Status

### Check 1 — Look-Ahead Audit: PASS

This is the highest-stakes check — an entirely new architecture (`src/crypto_trade/strategies/ml/cross_sectional.py`, 1073 lines) with new code. I audited it end-to-end across the four surfaces flagged in the dispatch.

**(a) The label.** `label_cross_sectional_rank` (lines 117-175) computes `_fwd_close = groupby("symbol")["close"].shift(-horizon)` then `_r_fwd = _fwd_close/close - 1`. This is the prediction *target* — forward-looking by definition of a label, which is correct. The within-symbol `shift(-3)` is groupby-safe (it does not bleed one symbol's close into another's). The tercile grade is then computed per-timestamp via `groupby("open_time")["_r_fwd"].transform(_tercile_grade)` (line 174) — a *contemporaneous* cross-sectional operation, again correct because it is the label. The label never re-enters the feature matrix: `CrossSectionalRankStrategy.feature_columns` is the explicit 13-feature list, and `_r_fwd`/`_fwd_close`/grade are never in that list. No label leak into features.

**(b) The panel builder.** `build_cross_sectional_panel` (lines 183-281) loads each symbol's parquet, applies a 180-bar listing burn-in, concatenates, then `_xs_rank_normalize` (lines 268-279) replaces each feature with its cross-sectional rank *within each `open_time` group*. This uses only the time-`t` cross-section — no future timestamp enters the rank. The 13 base features (the /059 anchor stack minus `btc_ret_14d`) are the past-only-audited /059 stack; the cross-sectional rank-transform of a past-only feature is still past-only. No leak in panel assembly.

**(c) The walk-forward / embargo.** `_generate_xs_monthly_splits` (lines 920-963) sets `train_end_ms = test_start_ms - embargo_ms` (line 951) with `embargo_ms = XS_REQUIRED_GAP * interval_ms` (line 718). This is the `e149e9d` look-ahead fix carried into the cross-sectional path. A training row at the last in-window timestamp `train_end_ms - 8h` has an H=3 forward label window reaching `train_end_ms - 8h + 24h = train_end_ms + 16h`. The embargo is `88 bars × 8h = 704h` — vastly larger than the 24h H=3 label window — so no training label's forward window can reach `test_start_ms`. The embargo is **conservative by ~29×** versus the bare H=3 requirement (the 88 includes the ×22 symbol-pooling factor; see Check 2). No train→test leak.

**(d) The PnL.** `run_cross_sectional_backtest` (lines 836-848): `idx_loc = ret_wide.index.searchsorted(ts, side="right")` then `next_ret = ret_wide[sym].iloc[idx_loc]` — `searchsorted(side="right")` returns the index *strictly after* `ts`, so `next_ret` is the `t→t+1` return, earned by a position decided at `t`. Correct — the decision precedes the return. The per-symbol vol estimate uses `ret_wide[ret_wide.index < ts].tail(50)` (line 816) — strictly past-only (`< ts`, not `<= ts`). No PnL look-ahead.

The OOS rank-IC is +0.043 — faint. A leaked rank-IC would be an order of magnitude higher (the IS T7 composite IC-IR is 0.195; a leaked OOS would be in that range or higher, not 0.043). The faint, positive OOS rank-IC is the signature of a real-but-weak *clean* signal, consistent with a leakage-free architecture. PASS.

### Check 2 — Embargo Width: PASS

`XS_REQUIRED_GAP = (XS_HORIZON + 1) * N_XS_SYMBOLS = (3 + 1) × 22 = 88` (`cross_sectional.py:83`). I verified the derivation independently. The pooled panel flattens one (symbol, timestamp) per row, 22 rows per timestamp. The label horizon is H=3 bars. López de Prado's purge requires removing, on both sides of every test boundary, all rows whose label window overlaps the test set: `(H+1)` timestamp-widths × `N` rows-per-timestamp = `4 × 22 = 88` rows in the flattened sequence. Correct.

It is wired with a hard self-assertion in **two** places: `_verify_xs_universe` (`run_cross_sectional_v3.py:111-116`, `RuntimeError` if `XS_REQUIRED_GAP != (H+1)×N`) and `_verify_xs_gap_assertion` (lines 165-175, an `assert`). And it is passed to `combinatorial_purged_cv` with `expected_gap=XS_REQUIRED_GAP` (`run_cross_sectional_v3.py:239`), which raises `AssertionError` on mismatch — the iter-v3/001 silent-rescale guard. The brief correctly distinguishes this from the legacy per-symbol `REQUIRED_GAP = 66 = (21+1)×3` and the runner does not conflate the two (separate runner, separate constant). PASS.

One observation, not a fault: in `_cv_rank_ic` (line 441) the Optuna inner CV converts the row-gap back to timestamp-steps via `gap_ts_steps = max(1, 88 // 22) = 4`, then purges 4 timestamp-steps from the end of train. 4 timestamp-steps = `H+1` — exactly the correct purge in timestamp units. Internally consistent.

### Check 8 — Hypothesis-Implementation Alignment: PASS

This is the check the dispatch flagged for an explicit read. **Check 8 tests "does the code match the brief," and it does — so Check 8 PASSES.** The engineering report's verdict 3b is correct and I independently confirm it:

- The `build_positions` code (`cross_sectional.py:582-587`): `order = np.argsort(scores)` (ascending), `long_syms = sorted_syms[:n_leg]` (lowest scores → LONG), `short_syms = sorted_syms[-n_leg:]` (highest scores → SHORT).
- Brief Section 3.4 step 2 verbatim: *"Long the bottom tercile of the predicted ranking ... and short the top tercile."* The code implements exactly this.

The conceptual error is in the *brief*, not the code. The `LGBMRanker(lambdarank)` is trained on `label_cross_sectional_rank` grades, where **grade is assigned by FORWARD-return rank** (grade 2 = top-third of forward returns). LambdaMART therefore learns the *forward* mapping: high predicted score → high future return. The engineering report's pooled IS Spearman confirms it — `Spearman(predicted_score, label_grade) = +0.0328, p=1.2e-12`. The brief's Section 3.4 parenthetical (*"the model's predicted forward-cross-sectional losers — which, given the reversal, are the recent winners"*) is a non-sequitur: it conflates the EDA's *past*-return reversal predictor (high past return → low future return, negative rank-IC) with what the model learns from a *forward*-return label. The model is not trained on past returns; it is trained on the forward grade, so it has no reversal to invert. The brief longs the model's predicted future *losers*. The per-leg PnL in the engineering report confirms the inversion: the long leg has negative gross (−0.3764 IS), the short leg positive gross (+0.2985 IS).

This is a brief-design finding for the QR, not an implementation defect and not a methodology BLOCK. The code is faithful; Check 8 PASSES. The sign error is recorded in Recommendation 1.

I also confirm there is no scope creep: the legacy `run_baseline_v3.py` per-symbol path is untouched (the engineering report and the brief Section 3.8 both state the cross-sectional path is a *separate* runner; I verified `run_cross_sectional_v3.py` is a new file importing from a new module). The re-architecture is exactly the registered hypothesis.

## Recommendations to QR

This iteration is a methodologically-clean NEGATIVE — recorded validly. The architecture and `cross_sectional.py` infrastructure are sound and worth retaining. My read on the Section 8 classification and three items for the corrected /089:

1. **Classification: this is NOT 8.2 ARCHITECTURE-FALSIFIED, and the QR should not file it as such — but it is also not 8.3.** Brief Section 8 evaluates SUSPICIOUS first (8.1), then ARCHITECTURE-FALSIFIED (8.2, fires iff F1 — OOS rank-IC ≤ 0). OOS rank-IC is **+0.043 > 0**, so F1 does *not* fire — 8.2 does not apply. But 8.3 (ARCHITECTURE-VALIDATED-PROMISING) requires OOS/IS Sharpe ≥ 0.5 AND `frac_positive_paths` ≥ 0.55 AND OOS Sharpe > 0 — and OOS Sharpe is −0.54 (F3 fires) and `frac_positive_paths` = 0.000 (F4 fires). So 8.3 does not apply either. The matching class is **8.4 ARCHITECTURE-PARTIAL**: OOS rank-IC > 0 (the cross-sectional signal *did* transfer, faintly) but non-F1 falsifiers F3/F4 fire (the long-short *construction* loses money). The QR's Section 8 final call should file /088 as **ARCHITECTURE-PARTIAL** — "signal transfers, construction underperforms" — which is materially different from "architecture falsified." The honest read: the +0.043 OOS rank-IC at t≈4.6 (n=1255) is weak but real and OOS-positive, exactly as a clean re-architecture's first build should look; the architecture is *not* falsified, the *position construction* is.

2. **The sign error is real and pre-registered as foreseeable — fix it in /089's brief, not as a post-hoc patch.** /089's brief Section 3.4 must specify the position mapping from first principles of what `lambdarank` on a forward-return-grade label learns: high score = predicted future winner → **LONG the top tercile, SHORT the bottom tercile.** Do not paper over it with a "reversal" narrative in a docstring (the `predict_ranking` docstring at `cross_sectional.py:511-515` is wrong and should be corrected). The engineering report's flipped-IS diagnostic shows even the *corrected* sign yields only IS gross Sharpe ≈ +0.07 — so the sign fix alone is necessary but far from sufficient.

3. **Turnover is the dominant failure mode — /089 must attack it structurally, and the brief must pre-register a turnover budget.** IS fees (0.69) are 8.8× IS gross PnL (0.078); the every-8h-bar rebalance at 0.1%/side with ~1/3-of-book turnover/bar is incompatible with a +0.043 rank-IC. /089 should test a slower rebalance (hold H=3 bars, rebalance every 3rd bar, not every bar — the brief's own Section 3.4.1 already half-acknowledges this with "overlapping 3-bar holds"), a no-trade band (only rebalance a symbol when its target weight moves > threshold), or a wider universe so the signal-per-unit-turnover improves. The brief should pre-register a turnover ceiling (e.g. gross turnover/bar < X) as a hard gate so /089 cannot rationalise the same drag post-hoc. Separately: /089 should fix the `_compute_xs_cpcv` path-Sharpe proxy (`run_cross_sectional_v3.py:247-273`) — it currently correlates label grades with themselves and collapsed to 45 rows of `sharpe=0.0`; the CPCV path metric must run the trained model on each path's test fold and compute the actual long-short net return, or F4 remains an uninformative gate.

My overall read for the QR's Phase 8 diary: the cross-sectional architecture is **worth a corrected /089** (ARCHITECTURE-PARTIAL, not falsified). The OOS rank-IC transferred positive and the diagnoses are precise and actionable — sign inversion and turnover drag are both fixable. /088 is a clean, honest, well-instrumented re-architecture EXPLORATION that did its job: it produced a runnable architecture and a faint-but-positive generalising OOS signal, and it diagnosed exactly what /089 must fix. Recorded as ARCHITECTURE-PARTIAL; merge the methodology record; BASELINE_V3.md stays `v0.v3-059`.
