## 1. How `fetch-oi` works (inspected, `src/crypto_trade/main.py:1412`)

- `uv run crypto-trade fetch-oi --symbols A,B,C [--output-dir DIR]`. No date flags.
- Downloads `data.binance.vision/data/futures/um/daily/metrics/<SYM>/<SYM>-metrics-YYYY-MM-DD.zip`
  (5-min granularity) for every day 2020-09-01 → yesterday, resamples to 8h, writes
  `data/open_interest/<SYM>/8h.csv`.
- Schema (7 cols): `open_time, sum_open_interest, sum_open_interest_value,
  count_toptrader_long_short_ratio, sum_toptrader_long_short_ratio, count_long_short_ratio,
  sum_taker_long_short_vol_ratio`. OI columns = LAST 5-min reading in the bar window;
  count/sum columns = SUM over the window.
- "Incremental" = dedup on `open_time` only — a re-run still re-downloads the entire date range
  (~2,138 requests/symbol, ~0.65 s each). Budget accordingly; there is no day-level skip.
- Storage: `data/open_interest` in this worktree is a **symlink to the main trunk**
  (`/home/roberto/crypto-trade/data/open_interest/`) — same sharing pattern as the kline dirs.
  Backfilled data is visible to all worktrees.
- Day-level failures: 3 retries then WARN + continue (day silently absent from cache). Zero
  WARNs occurred in the priority run.

## 5. Data-quality findings (LOUD — read before writing DIAG-C)

1. **Global one-bar outage:** every symbol is missing the same single bar, 2024-02-16 16:00 UTC
   (archive-side). Harmless cross-sectionally (missing for everyone); do not forward-fill.
2. **00:00-bar stub artifact (the big one).** In several archive eras (nearly all of 2022 and
   2025-2026, part of 2021/2024), the 00:00 UTC bar is built from a SINGLE 5-min row instead of
   ~96 (daily-ZIP boundary quirk). Exactly 1,811 of 5,046 bars (~36%) per 2021-12 symbol.
   Consequences:
   - `sum_open_interest` / `sum_open_interest_value` remain VALID (a real point-in-time snapshot,
     no lookahead) — but on stub bars the snapshot is taken at the window START, not the end.
   - The flow SUM columns (`sum_taker_long_short_vol_ratio`, `sum_toptrader_long_short_ratio`,
     …) are NOT comparable across bars: a stub bar sums ~1 interval vs ~96. **Any consumer must
     normalize by the paired `count_*` column (sum/count = per-interval mean), never use raw
     sums.** This directly affects the DIAG-C crowding score's taker-imbalance input (the frozen
     spec says taker-imbalance z — the panel's own complete `taker_buy_volume/volume` is an
     alternative input already used by DIAG-D; that choice is the QR's, not mine).
3. **Final cached bar is provisional:** the last bar per symbol is a 1-row day-boundary stub
   that fills in on the next fetch. Live-ish consumers should drop or refresh the final bar.
4. **Delisting wind-down degradation:** dying contracts (BUSD pairs Dec-2023+, MATIC Sep-2024+,
   EOS May-2025+) show 1-2 missing bars/day for weeks before their archives stop. PIT top-N
   membership by $-volume naturally exits these names as volume dies, so exposure is limited —
   but OI features must tolerate NaN bars without forward-filling across gaps.
